# Caller assessment, kc-axi spec, by access-control

Date: 2026-10-27
Spec under review: `libs/kc-axi/README.md` (Draft v0.2)
Caller: `umas/modules/access-control/access-control-spec.md` (sections 2, 3.1, 4, 5.3, 5.6, 7, 8, 9 items 6, 7 and 12, AXI section)
Live-test facts: kc-axi section 11 (Keycloak 26.6.4, rootless Podman on macOS). Treated as facts.

## Verdict

**REJECTED.** `umas init` cannot be built against this spec as written. Five blockers stop it. It cannot write a valid config file, because the field allow-list is not defined. It cannot find kc-axi's own configuration. Its first run fails on the missing secrets file. It cannot learn the Admin's `sub`. The audience mapper that every token check depends on is not defined.

## Needs a user decision

1. **Stable key for a service principal (gap 11; access-control N6).**
   - (a) Map by `clientId`, read from the token's `azp` or `client_id` claim. It is stable across a realm rebuild, and kc-axi needs no change beyond gap 20.
   - (b) Map by the service account's `sub`. kc-axi must expose the service-account user id and keep client ids across a rebuild, which was not tested.
   - **Recommendation: (a).** It needs no new kc-axi interface and survives `down --purge`.

2. **How client secrets reach each service (gaps 14 and 16).**
   - (a) Each service reads the shared secrets file. This is the current text. It is simple, but every service can read every secret, and the file must be hidden from Worker sandboxes.
   - (b) The UMAS launcher reads one client's secret through a kc-axi library function and passes it to that service only, in its environment. Services never open the file, and agent-execution denies the kc-axi directory to sandboxes.
   - (c) An OS keychain per client. Least exposure, but it needs a cross-platform keychain dependency in kc-axi.
   - **Recommendation: (b).** It meets access-control 5.5 and section 2 ("in the environment") without a new dependency. It needs the reader function from gap 14.

3. **How `umas init` gets the Admin `sub` (gap 4).**
   - (a) `umas init` generates a UUID, writes it as `id` in the users file, and stores it before `apply`. `partialImport` keeps the id (item 8).
   - (b) kc-axi adds a lookup by username that returns the id.
   - **Recommendation: both.** Use (a) for a new Admin. Use (b) for an Admin who already exists in Keycloak, so that a re-run of `init` stays idempotent.

4. **Removing a service principal on an `umas init` re-run (gap 9).**
   - (a) `umas init` passes `--allow-delete`, so a removed `service_principals` entry deletes its client.
   - (b) `umas init` never deletes. It sets `enabled: false` in the config file, and the Admin removes the client explicitly.
   - **Recommendation: (b).** Deleting an identity silently is the riskier error. A disabled client fails introspection at once (if gap 19 confirms it).

5. **Issuer hostname (gap 18).**
   - (a) kc-axi adds a `hostname` setting, passed as `KC_HOSTNAME`, with the default taken from `base_url`.
   - (b) There is no kc-axi change, and every UMAS client must use `base_url` exactly.
   - **Recommendation: (a).** Rule (b) breaks the first time a browser redirect uses `localhost`.

6. **How `umas init` calls kc-axi (gap 6; kc-axi item 12 leaves it to the caller).**
   - (a) As a subprocess, using `--json`.
   - (b) As the Python library.
   - **Recommendation: (a).** It matches access-control 3.1, and it keeps the admin credential out of the long-running UMAS process. It needs the `--json` contract for `plan` and `apply` from gap 6. Access-control 3.1 must then drop "calls the admin REST API directly" (gap 35).
