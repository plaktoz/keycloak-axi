# Caller assessment: kc-axi, external reuse

Date: 2026-10-27 · Spec assessed: [README.md](../../README.md) (Draft v0.2) · Read with: `libs/README.md` in agentzero-v2-dev
Perspective: an engineer at an unrelated company, no knowledge of UMAS, who wants a local Keycloak managed as desired state from their own repo and CI, driven by a coding agent.

Method: the spec was read in full and checked against itself, against libs/README.md, and against its own section 11 facts. Section 9 was used only to identify UMAS-specific content. No UMAS requirement was treated as a requirement. Nothing was run; no live Keycloak was contacted.

**Verdict: REJECTED.** Five blockers: the config and users schemas are undefined; a missing secrets file blocks the first apply; `plan_hash` cannot detect the change `--expect` exists to catch; export followed by plan fails for any realm with a hand-made client; and apply can report a refusal after it has already written changes.

## Needs a user decision

1. **Scope: local dev only, or remote and CI too (rows 6, 22, 32).**
   - Option a: local dev only. Remote writes are refused and CI is not supported. This contradicts section 4, which already claims remote use.
   - Option b: remote and CI supported. Adds `ca_file`, `--allow-remote` on every write, and a CI step that restores the secrets file before apply.
   - Recommendation: b. It matches the spec's own claim and the consumer's stated CI use. It adds TLS work and a CI secrets model.

2. **Where secret values live (rows 2, 15, 22, 44).**
   - Option a: a local JSON file only. CI restores it from its own secret store before apply.
   - Option b: also accept a value from the environment on first create.
   - Option c: an external secret store behind an adapter.
   - Assessment: a is what the spec describes. It fails on the first run unless row 2 is fixed. b adds a second source of truth. c is a larger design with no current consumer.
   - Recommendation: a, with the row 2 rule and the server identity in the file (row 15). Defer c.

3. **One owner or several owners per realm (row 18).**
   - Option a: one owner per realm, enforced by refusing a file whose marker names another owner.
   - Option b: an owner name in the marker, and removal only for clients with the same owner.
   - Assessment: a blocks legitimate layering (base plus overlay). b changes the marker format, so the spec's schema version moves.
   - Recommendation: b.

4. **Which fields the config file owns, and how many fields v1 supports (rows 1, 36).**
   - Option a: declared fields only, as written. A field removed from the file stays on the server.
   - Option b: removed fields reset to Keycloak defaults. Destructive, and needs a default table for every field.
   - Scope option c: a fixed v1 list of about ten realm and client fields.
   - Scope option d: full pass-through of Keycloak's representation.
   - Recommendation: a and c. Drift from removed fields is documented rather than silently reset, and the list is small enough to test.

5. **Is `id` required on every user (row 8).**
   - Option a: required. The `sub` stays stable across a rebuild, as section 3.4 promises.
   - Option b: optional, matched by username. The stability promise is dropped.
   - Recommendation: a.

6. **Emergency disable: does the next apply undo it, and are sessions revoked (row 14).**
   - Option a: apply refuses to re-enable a user changed outside the file, unless `--allow-reenable` is given. Sessions are revoked through the admin endpoint.
   - Option b: as written, the next apply restores `enabled` from the file.
   - Assessment: b reverses an emergency action silently in an automated run. Session revocation is not tested, so it cannot be promised yet.
   - Recommendation: a, and test session revocation before the spec claims it.

7. **Supported Keycloak versions (rows 23, 33).**
   - Option a: 26.6.4 only, refuse everything else.
   - Option b: a named 26.x range, each release tested at both ends, with a version gate in `status` and refusal outside the range.
   - Option c: no statement. This is the current state.
   - Recommendation: b, starting with 26.6.4. Option c leaves row 33 open.

8. **Adopting a client that has a live secret (row 16).**
   - Option a: on adopt, capture the live secret into a new generation, then manage it. Consumers that use the live value keep working.
   - Option b: overwrite the live secret with the file's generation. Breaks any consumer that is using the live value, silently.
   - Recommendation: a.

9. **Admin password change and volume persistence (rows 23, 25, 33).**
   - Today a changed `KC_ADMIN_PASSWORD` with an existing volume has no tool path except `down --purge`, which deletes the realm data.
   - Option a: document purge and rebuild, with data loss unless exported first.
   - Option b: add a command that changes the admin password through the REST API. Not tested.
   - Recommendation: a now, then b after a test on 26.6.4.
